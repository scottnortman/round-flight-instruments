## Integration issues found and resolved

The first board attempt starved the state owner. The minimal regression
scripts/check-display-startup.py recorded a failed display with one frame, owner
age 321 ms and render time 250 ms. The owner latched a timing fault; the task
watchdog reset the board. The backlight stayed off. Captured evidence is
[startup failure](display-startup-red.json) and [UART boot log](display-first-boot.log).
The decoded backtrace placed the worker in framebuffer pixel drawing.

Explicit priority 10 for the state owner (default main priority was 1; pthread
workers were 5) removed owner starvation while leaving render time high. The
startup regression then passed, isolating scheduling as the owner-fault cause.
The user observed flicker and a red X: missing startup input correctly caused
the red X, while long render intervals exceeded the presentation lease and
triggered repeated blanking.

Raster optimization was then restricted to the UI crate, using a concrete
draw_frame entry point so generic pixel code is compiled there. Rendering fell
below the unchanged presentation budget. A steady probe had zero guard blanking,
and the user confirmed the displayed gauge. The guard now has priority 11,
above owner 10 and renderer/other workers 5, so it can preempt a busy owner too.
No freshness/watchdog threshold was relaxed.

Concurrent IMU testing then reproducibly failed initialization with Bus(263),
an I2C timeout. Pausing rendering allowed the same sensor to start while RGB
scanout continued. Raising only the IMU worker's priority from 5 to 6 fixed the
original initialization/audit/estimator check, including a valid rendered gauge.
The board now scopes the spawn configuration to that worker; the portable IMU
service remains independent of ESP-IDF. No I2C timeout was extended. The regression
also verifies advancing display frames and no guard blanking during IMU checks.
Evidence: [failure](imu-with-display-red.json),
[repeat failure](imu-with-display-repeat.json),
[render-pause probe](imu-render-pause-probe.json), and the passing concurrent report.
This scheduling interaction makes concurrent peripheral/display testing a required
check for subsequent render or task-priority changes.

The Xtensa compiler also rejected a generated float constant lookup table for
tick dimensions. Disabling SLP vectorization did not fix it and was reverted.
Keeping the exact integer dimensions opaque until conversion avoids that code
generation path; geometry tests remain unchanged. A trial optimizing the entire
board crate produced incorrect display=off CLI metadata despite a true managed
argument. That broader profile was rejected; control/FFI remains on its earlier
size profile, with hardware startup now asserting display=managed. The underlying
compiler anomaly has not been fully minimized; do not re-enable broad optimization
without reproducing/investigating it and rerunning hardware protocol checks.

Changing compiler flags created multiple IDF build directories. Build/flash
scripts now read Cargo's exact build-script/executable JSON results and save a
hash-checked artifact manifest. They no longer select a bootloader by a wildcard
or most-recent directory.

## Firmware and limits

Archived in artifacts/first-gauge-20261101 with ELF, matching bootloader,
partition CSV, SDK config, lockfile and source snapshot. Factory backup and older
console/IMU firmware are retained.

- Application image: 890000 / 1048576 bytes (84.88%).
- ELF SHA256: 41a0fd445dd5733dde225306017d6ea3d11c9543b13b6646a86716caf671daa3.
- Rust ESP toolchain: 1.97.0-nightly, 8ea53bcd7, 2026-07-08; ESP-IDF 5.5.5.
- This implementation does not meet a 30-rendered-fps target; it is the first
  correctness-focused gauge baseline. Display refresh and rendered-frame cadence
  are different. Further rendering optimization precedes a moving attitude gauge.
- The barometric calculation deliberately preserves the handoff's simulation
  model. It is not a validated operational air-data model.
- IMU data still cannot feed gauges; the stationary Y gyro offset is unresolved.
- Touch, attitude rendering, other gauges, persistence and faster communications
  remain future work. The single-gauge stage does not complete the earlier
  altimeter-plus-attitude/touch milestone.
- No independent hardware fail-dark circuit or worst-case timing proof is claimed.
  Fault injection covers task/submission stalls, not electrical DMA/panel faults.

Reboot deliberately starts with missing inputs and an ALT DATA/MISSING face.
Use sim preset level and sim resume to display simulated values.

Final running state: altimeter, simulated 4520 ft, barometer 29.92 inHg,
simulation running, display on in gauge mode, and IMU off.
